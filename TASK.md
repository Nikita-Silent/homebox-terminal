# Homebox Inventory Terminal — ТЗ на разработку

## 1. Цель проекта

Разработать отдельный веб-интерфейс поверх **Homebox** для быстрого перемещения оборудования между складами, помещениями и полками.

Приложение должно работать как терминал складского учёта с поддержкой сенсорного экрана, сканера штрихкодов и ручного поиска оборудования.

**Homebox остаётся основной системой учёта.** Новый интерфейс не должен дублировать его функциональность, а должен упрощать складские операции.

## 2. Технологический стек

- **Nuxt 4 + Vue 3 + TypeScript**
- **Vite** — сборка
- **Tailwind CSS 4** — стили
- **shadcn-vue** — UI-компоненты
- **Nuxt Server Routes** — серверный API/BFF
- **Homebox API** — получение и изменение данных
- **Docker** — развёртывание

На этапе MVP не использовать отдельную базу данных, отдельный backend или Pinia без необходимости.

API-ключ Homebox хранится исключительно на сервере, в переменных окружения.

## 3. Учёт оборудования

Необходимо поддерживать две модели:

**Поштучный учёт**

Каждый физический экземпляр оборудования представлен отдельным Item с собственным идентификатором (UID).

Пример:

- TP-Link ER605 №1 — UID 1
- TP-Link ER605 №2 — UID 2

Каждый экземпляр можно перемещать независимо.

**Количественный учёт**

Несколько одинаковых экземпляров представлены одним Item с полем `quantity`.

Пример:

- D-Link DGS-1005C — 3 шт.
- Переместить 1 шт. на другой склад.
- На исходном складе остаётся 2 шт., на целевом появляется 1 шт.

При частичном перемещении необходимо корректно разделять количество между локациями, сохраняя данные оборудования.

## 4. Основные экраны

### Главная

- Кнопка «Найти оборудование»
- Кнопка «Сканировать»
- Кнопка «Переместить»
- Быстрый доступ к основным операциям

### Поиск оборудования

- По названию
- По артикулу
- По UID
- Через сканер штрихкода или QR-кода
- Отображение найденных Item

### Карточка оборудования

- Название и изображение
- UID / артикул
- Текущая локация
- Доступное количество
- Кнопка «Переместить»

### Перемещение

- Откуда перемещается оборудование
- Куда перемещается оборудование
- Выбор количества (если `quantity > 1`)
- Иерархическое дерево локаций
- Подтверждение операции

### Результат

- Успешное перемещение
- Отображение новой локации и количества
- Понятное сообщение об ошибке при неудаче
- Возможность сразу перейти к следующему оборудованию

## 5. Логика перемещений

Основной процесс:

1. Пользователь находит или сканирует оборудование.
2. Система загружает его из Homebox.
3. Пользователь выбирает количество и целевую локацию.
4. Система проверяет корректность операции.
5. Пользователь подтверждает перемещение.
6. Сервер выполняет операцию через Homebox API.
7. Интерфейс показывает результат.

**Требования к транзакционности:**

- Не допускать отрицательных остатков.
- Не допускать повторного выполнения одной операции.
- Проверять актуальное количество перед изменением.
- Исключить потерю оборудования при частичном перемещении.
- Не показывать успешное выполнение до подтверждения сервером.
- Корректно обрабатывать ошибки API и сетевые сбои.

Важно: возможности атомарных операций Homebox API необходимо проверить до реализации. Если частичное перемещение требует нескольких API-запросов, разработчик должен предусмотреть механизм согласованности данных. Обычная последовательность запросов не гарантирует транзакционности. Если без дополнительного хранилища гарантии обеспечить невозможно, это должно быть отдельно отражено в архитектуре.

## 6. Интерфейс

Основные требования:

- Минималистичный дизайн.
- Touch-first / kiosk-friendly.
- Крупные кнопки и области нажатия.
- Адаптация под планшет и компьютер.
- Минимальное количество действий для перемещения.
- Поддержка системной экранной клавиатуры.
- Поддержка USB-сканера в режиме HID (клавиатуры).
- Индикация загрузки, ошибок и успешных операций.

Интерфейс должен быть рассчитан на сотрудника склада без технической подготовки.

## 7. Архитектура

```
Nuxt 4
├── Pages / UI
├── Components
├── Composables
├── Server API (BFF)
│   ├── Items
│   ├── Locations
│   └── Transfers
└── Homebox API
```

Взаимодействие с Homebox исключительно через серверную часть Nuxt.

Логика перемещения должна быть вынесена в отдельный сервис, независимо от UI.

Настройки подключения к Homebox задаются через ENV.

## 8. Что входит в MVP

- Поиск оборудования.
- Сканирование QR/штрихкодов.
- Просмотр карточки оборудования.
- Получение дерева локаций.
- Перемещение целого Item.
- Частичное перемещение количественного Item при обеспечении согласованности данных.
- Подтверждение операции.
- Обработка ошибок.
- Полноэкранный интерфейс терминала.
- Развёртывание через Docker Compose.

## 9. Что оставить на следующие этапы

- Журнал и аудит всех перемещений.
- Передача между сотрудниками.
- Двухэтапная передача «Отправить → Принять».
- Приёмка нового оборудования.
- Массовые перемещения.
- Инвентаризация.
- Печать этикеток.
- Этикетки полок 46×26 мм с крупными номерами 01–25 без QR-кода.

## 10. Критерии готовности

MVP считается готовым, когда сотрудник может:

1. Открыть интерфейс терминала.
2. Отсканировать оборудование или найти его вручную.
3. Увидеть текущий склад и остаток.
4. Выбрать другой склад либо полку.
5. Указать нужное количество.
6. Подтвердить перемещение.
7. Проверить результат непосредственно в Homebox.

Изменения должны сохраняться в Homebox, а не только отображаться в интерфейсе.

**Главный принцип:** максимальная скорость складских операций, минимальная сложность интерфейса и отсутствие рассинхронизации с Homebox.
